## Contexto

El taller de chapa y pintura **"El Novato"** operaba su relación con clientes enteramente por WhatsApp — presupuestos, fotos de daños, coordinación de turnos, todo en una bandeja de chats sin estructura. Cuando un cliente sufría un accidente, el proceso era manual, estresante y sin trazabilidad.

La plataforma que construí digitaliza ese flujo por completo, permitiendo a los clientes solicitar presupuestos desde casa, seleccionar áreas dañadas en un selector visual del vehículo, recibir un cálculo automático basado en la referencia **FAATRA**, agendar turno en el calendario del taller y recibir confirmaciones por WhatsApp. Del otro lado, el taller gestiona todo desde un dashboard administrativo con métricas, calendario, órdenes de trabajo y control de precios.

## El Problema y las Decisiones Técnicas

### 1. Motor de Presupuestos con Referencia FAATRA

El negocio del taller usa **paños** como unidad de medida: cada pieza del vehículo equivale a un paño, con excepciones como capot y techo que valen dos. El precio base es de $300 USD por paño, pero el taller necesita actualizar valores según la tabla **FAATRA** (referencia oficial del sector automotor).

Implementé un sistema de pricing en tres capas:

// src/lib/services/budget-calculation.ts
export async function calculateBudget(
  panelIds: string[],
  options?: { storeBudget?: boolean }
) {
  const config = await PricingConfiguration.findOne()
    ?? { basePricePerPanel: 300, panelExceptions: [], currency: 'USD' }

  const faatraRefs = await FAATRA.findOne()
  const breakdown: PanelBreakdown[] = panelIds.map(id => ({
    panelId: id,
    panelName: PANEL_LABELS[id] ?? id,
    multiplier: getPanelMultiplier(id),
    unitPrice: config.basePricePerPanel,
    subtotal: config.basePricePerPanel * getPanelMultiplier(id),
  }))

  return {
    totalAmount: breakdown.reduce((s, b) => s + b.subtotal, 0),
    panelCount: breakdown.length,
    breakdown,
    exceptionsApplied: config.panelExceptions,
    currency: config.currency,
    calculationTimeMs: Date.now() - start,
    faatraReferences: !!fatraRefs,
  }
}

export function parseFAATRACSV(csvString: string): FAATRAReference[] {
  return csvString
    .trim().split('\n')
    .slice(1) // skip header
    .map(line => {
      const [panelId, panelName, referencePrice] = line.split(',')
      return { panelId, panelName, referencePrice: Number(referencePrice) }
    })
}

### 4. Sistema de Encriptación a Nivel de Aplicación

Datos sensibles (teléfono, cédula, tokens OAuth) se encriptan con **AES-256-CBC** antes de persistir en MongoDB, usando getters/setters de Mongoose:

```ts
// src/lib/utils/encryption.ts
const ALGORITHM = 'aes-256-cbc'
const KEY = crypto.scryptSync(ENCRYPTION_KEY, 'salt', 32)
const IV_LENGTH = 16

export function encrypt(text: string) {
  const iv = crypto.randomBytes(IV_LENGTH)
  const cipher = crypto.createCipheriv(ALGORITHM, KEY, iv)
  const encrypted = Buffer.concat([cipher.update(text, 'utf-8'), cipher.final()])
  return { iv: iv.toString('hex'), encryptedData: encrypted.toString('hex') }
}
```

### 5. Rate Limiting con Fallback

Implementé rate limiting en Redis con un fallback transparente a memoria. Si Redis falla, el sistema sigue funcionando — registra el evento y permite el tráfico:

```ts
// src/lib/utils/rate-limiter.ts
const tiers = { default: 20, strict: 5, webhook: 30, public: 10 }

export async function rateLimit(request: Request, tier = 'default') {
  const ip = getClientIp(request)
  const limit = tiers[tier]

  if (redisAvailable) {
    const [count] = await redis.multi()
      .incr(`ratelimit:${ip}`)
      .expire(`ratelimit:${ip}`, 60)
      .exec()
    if (count > limit) return rateLimitResponse(limit)
  } else {
    // Fallback in-memory
    const entry = memoryStore.get(ip)
    if (entry && entry.count > limit) return rateLimitResponse(limit)
    // ...
  }
}
```

## Flujo Completo del Usuario

```
DESCUBRIMIENTO → SOLICITUD → PRESUPUESTO → TURNO → EVALUACIÓN → ORDEN → REPARACIÓN → ENTREGA
```

**María (cliente):**
1. Llega al sitio desde Google, ve antes/después y reseñas
2. Inicia sesión con Google OAuth (un click) o se registra
3. Completa formulario multi-paso de 4 etapas: datos personales → vehículo → daños (selector visual + fotos) → revisión
4. Recibe presupuesto aproximado instantáneo basado en FAATRA
5. Selecciona turno en el calendario (slots en vivo desde Google Calendar)
6. Recibe confirmación por WhatsApp
7. Recibe recordatorios automáticos 24h y 2h antes

**Juan (técnico):**
1. Ve dashboard con turno más cercano y métricas del día
2. Revisa solicitud entrante con fotos y selector de daños
3. Acepta turno → cliente recibe WhatsApp automático
4. Evalúa el auto en persona, ajusta presupuesto final desde el panel
5. Genera orden de trabajo y la mueve por 7 estados (pendiente → programado → en progreso → en pintura → control de calidad → completado → entregado)
6. Genera PDF profesional para aseguradoras con formato A/B/C
7. Gestiona precios base, excepciones y valores FAATRA desde el panel

## Lecciones Aprendidas

- **Fallbacks primero, features después**: Implementar rate limiting con fallback a memoria (si Redis cae), calendario local de respaldo (si Google Calendar falla), y notificaciones manuales (si WhatsApp falla) nos salvó en múltiples ocasiones durante desarrollo. Cada integración crítica debe tener su plan de contingencia documentado.

- **Encriptación con getters/setters de Mongoose**: Aplicar encriptación AES-256 a nivel de campo usando los getters y setters nativos de Mongoose fue una decisión que mantuvo el código de negocio limpio — los servicios nunca manejan lógica de encriptación, solo leen y escriben strings.

- **Selector visual > texto libre**: El selector de 5 vistas del vehículo con CSS Grid y botones semánticos no solo mejoró la calidad de los datos recibidos (el técnico ve exactamente qué áreas están dañadas), sino que redujo la fricción del formulario. La validación Zod de "al menos un área" asegura solicitudes completas.

- **Un solo monolito, pero modular**: La arquitectura de service layer con dominios separados (auth/, calendar/, whatsapp/, images/, pdf/, pricing/) dentro de `src/lib/services/` permitió avanzar rápido sin perder la capacidad de extraer microservicios en el futuro. Cada servicio tiene su propia interfaz, manejo de errores y tests.

- **Máquina de estados para el bot de WhatsApp**: Implementar el bot con una state machine explícita (`initial → collecting_name → collecting_phone → …`) hizo que el flujo conversacional fuera predecible, testeable y fácil de extender. Las sesiones en Redis con TTL evitan que sesiones abandonadas consuman memoria.

- **20 mil líneas de TypeScript, 55 componentes, 33 días**: El ritmo fue posible gracias a Zod para validación en frontend y backend (errores atrapados en compilación, no en producción), al tipado estricto de TypeScript y a los componentes reutilizables del design system con dark mode.
